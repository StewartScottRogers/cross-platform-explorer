## Summary
Reviewer follow-up from CPE-1170 (PR #486, merged). `gui-smoke/lib/compare.ts`'s `decodePng`
implements the full PNG scanline-filter set (None/Sub/Up/Average/Paeth, spec section 9.2), but its
companion `encodeRgbaPng` only ever emits filter type 0 (None). Since the CPE-1170 unit suite
(`gui-smoke/lib/compare.test.ts`, 15 tests) builds all of its fixtures via `encodeRgbaPng`, only the
None branch was ever exercised — the Sub/Up/Average/Paeth predictor branches, which are exactly the
ones that decode LIVE Chromium/WebView2 screenshots (real encoders pick filters adaptively per row),
had zero test coverage. A silent regression in any of those four predictors would have slipped
through `npm run test:unit` undetected.

## Acceptance Criteria
- [x] New unit tests hand-construct valid PNG buffers (independent of `encodeRgbaPng`) whose IDAT
      scanlines use filter types 1 (Sub), 2 (Up), 3 (Average), and 4 (Paeth), and assert `decodePng`
      reconstructs the exact original pixel bytes for each.
- [x] Coverage includes an RGBA (colorType 6) image with a different filter on each of 4 rows, plus a
      separate all-Paeth RGB (colorType 2) image, per the ticket's suggested shape.
- [x] Each fixture's filter bytes are independently confirmed to be 1-4 (not 0) by inflating the IDAT
      and reading the first byte of every scanline directly — not just trusted from construction code.
- [x] Confirmed the new tests would actually catch a broken predictor: temporarily mutated the Paeth
      defilter arithmetic in `decodePng` and reran the suite — exactly the two Paeth-exercising tests
      failed; reverted, suite green again.
- [x] `decodePng`'s unsupported-format guards (16-bit depth, interlaced, palette colorType 3) assert a
      clear, named thrown error rather than mis-decoding.
- [x] No new dependency — Node builtins only (`zlib`), consistent with CPE-1170; `package-lock.json`
      untouched.

## Work Log
- 2026-07-31 — **Built.** Added `gui-smoke/lib/compare.filters.test.ts` (sibling test file, picked up
  by the existing `test:unit` glob `tsx --test lib/**/*.test.ts`, no script change needed):
  - Reimplemented the minimal chunk/CRC32 assembly `encodeRgbaPng` uses internally (not exported from
    `compare.ts`, so copied locally for fixture construction — same structure, same CRC table).
  - Wrote `filterScanline()`: the PNG-spec *encode-side* filter transform (Sub/Up/Average/Paeth),
    the arithmetic inverse of the *defilter* switch in `decodePng`, applied per scanline against
    known "true" (unfiltered) pixel bytes and the true previous row (all-zero for row 0, per spec).
  - `buildFilteredPng()` assembles a full valid PNG (IHDR/IDAT/IEND, deflated scanlines) from raw
    pixel rows + a per-row filter-type array.
  - Pixel bytes are generated by a small non-uniform formula (`(x*37 + y*61 + c*17 + 5) % 256`) so
    neighbouring bytes (a/b/c) are never trivially equal/zero — guards against a fixture that would
    "accidentally" decode correctly even with a broken predictor.
  - Three coverage tests: (1) 5x4 RGBA image, one row each of Sub(1)/Up(2)/Average(3)/Paeth(4); (2)
    6x5 RGB (colorType 2) image, all 5 rows Paeth(4) — rows after the first have a genuine non-zero
    previous row, so Paeth actually branches among a/b/c rather than degenerating to the row-0 case;
    (3) a minimal 2-row all-Up(2) RGBA image covering the b=0 edge case on row 0.
  - Each test independently re-inflates its own constructed IDAT (separate from calling `decodePng`)
    and asserts the scanline-leading filter-type bytes are exactly the intended 1-4 values, so the
    "these fixtures really exercise non-zero filters" claim isn't just asserted, it's checked.
  - Three more tests assert `decodePng` throws a clearly-named error for 16-bit depth, interlaced,
    and palette (colorType 3) inputs, via minimal IHDR-only PNGs (no IDAT needed — the guard throws
    before decode reaches the pixel data).
