## Summary

`.github/workflows/release.yml:402` sets

    VERSION=$(date +%s)

— a fresh Unix timestamp **at publish time**, stamped uniformly across every catalog entry. The
version therefore records *when the workflow ran*, not *what it published*.

So re-running the release workflow on an **old tag** publishes that tag's old manifests under a
version newer than everything currently installed. The catalog's anti-rollback rule compares
versions, so it **accepts** them. The content goes backwards; the number goes forwards.

## Why this is worth a High

PR #1051's Security Auditor called this out as the one route where the engine's core assumption —
**version monotonicity implies content freshness** — is simply false, and noted the part that decides
the priority:

> It is reachable **without signing-key compromise** — anyone who can trigger an Actions re-run on an
> old tag.

Everything is correctly signed. Every integrity check passes. The bundle is genuinely what that tag
published. The engine has no way to notice it is old, because the only freshness signal it has was
generated by the act of publishing it.

## The fix does NOT need a new trust surface

CPE-1924's author considered this and framed the fix as requiring `catalog-sign` to fetch and *trust*
the previously published index at publish time — new network access plus a new trust dependency in
the release pipeline, for what looked like a cosmetic win. The auditor corrected that framing and the
correction is the useful part of this ticket:

> Deriving `VERSION` from the tag's own commit timestamp, or from a counter committed to the repo,
> fixes it with **no new network or trust surface**.

Both alternatives are local to the checkout the workflow already has. **Do not inherit the
"not worth it" framing** — it was reasoned from the more expensive option.

## Acceptance criteria

- [ ] Replace `date +%s` with a version derived from **the content or the tag**, not from wall-clock
      publish time. The tag's commit timestamp and a repo-committed counter are both viable; pick one
      and say why. Whatever is chosen must be **monotonic for genuinely newer content** and must
      **not** advance when an older tag is republished.
- [ ] **Demonstrate the bug first.** Publish a fixture catalog from an "old tag" state, then re-run,
      and show the older content being accepted by the current engine. A fix landed without the
      reproduction is a fix nobody can prove worked.
- [ ] Then show the same sequence refused after the change, and show a legitimate newer release still
      being accepted. Both directions, or it is not a fix.
- [ ] Check what a version-scheme change does to **already-installed** clients: an installed base
      holding timestamp versions in the billions must not be permanently newer than every future
      commit-derived version. This is the part most likely to go wrong — say explicitly how the
      transition works, and cover it with a test.
- [ ] Consider whether the manifests should carry a **content** identity (they already have a
      sha256) that the engine can compare, so freshness stops resting on a number chosen at publish
      time at all. If that is out of scope, say so.

## Work Log

**2026-08-27 — implemented.**

**Reproduced first.** `sidecar/host/tests/catalog_republish_downgrade.rs` drives the real publish path
(`catalog::sign_bundle`, what `catalog-sign` calls) and the real apply path (`catalog::apply_bundle`,
what the host runs on a fetched bundle).
`republishing_an_old_tag_is_accepted_under_publish_time_versions` publishes v1, publishes v2, then
re-runs the v1 tag with a `date +%s` taken later — and the bundle is **Applied**: the on-disk manifest
reverts to v1's bytes and the recorded version becomes larger than the real newest release, so the
genuine v2 can never be re-applied either. Asserted on the *content*, not just on the verdict enum.

**Scheme chosen: the tagged commit's committer timestamp** (`--format=%ct`), read from the checkout the
job already has — no network, no new trust dependency. `%ct` not `%at`, because a rebase or cherry-pick
refreshes `%ct`, so it tracks the order commits actually landed. New file
`.github/workflows/scripts/catalog-version.sh` is the single definition of the rule; `release.yml`'s
`catalog` job now derives the version in a dedicated, fatal step and hands it to the signer by step
output (`test -n "$VERSION"` there, so an empty value can never be signed).

**Installed-base transition.** Both schemes emit Unix epochs, so the numbering is continuous — which is
exactly why a repo-committed counter was rejected: it would restart at a small integer against an
installed base holding ~1.79 billion and refuse every future release, permanently (red-proofed by
`a_repo_committed_counter_would_have_bricked_the_installed_base`). The real high-water mark was
measured rather than assumed: the last published `catalog-index.json` (release `v0.57.32`) carries
`version: 1784951108` on all 12 entries. `CATALOG_VERSION_FLOOR=1787000000` in the script is a fatal
publish-time check that the derived version clears it, and
`the_floor_clears_the_installed_base_so_the_first_commit_derived_release_is_an_upgrade` runs that
transition through the real engine (installed at 1784951108, first post-fix bundle at the floor →
Applied), reading the floor out of the shell script so the two can never drift apart.

**Both directions proven.** `republishing_an_old_tag_is_refused_under_commit_time_versions` → Rollback,
content stays put; `a_genuinely_newer_release_is_still_accepted_under_commit_time_versions` → Applied;
`re_running_the_current_tag_is_already_current_not_a_rollback` → AlreadyCurrent.
`src/lib/catalogPublishVersion.test.ts` guards the publish side: structural (via `parseYaml`) plus
executed against a purpose-built two-commit fixture repository, proving an older ref yields a smaller
number however late it is asked for. Sabotage-checked in both directions — restoring
`VERSION=$(date +%s)` in `release.yml` turns 4 of those tests red, and lowering the floor below
1784951108 turns the Rust transition test red.

**Residual, stated rather than hidden:** re-running a tag cut *before* this change executes that tag's
own copy of `release.yml`, which still reads a clock. No edit here can reach it. That legacy window
closes operationally — rotate `CPE_CATALOG_SIGNING_KEY` (an old tag's `catalog` job then finds no key
and publishes nothing), restrict who may re-run workflows, or raise the floor past whatever a stale
re-run stamped.

**Content identity (last criterion): answered, not implemented.** sha256 gives *identity* but not
*order* — it can say "this is not the same content", never "this is older content" — and the persisted
state (`VersionMap`, an id → u64 map) keeps no history of hashes to rank a candidate against. The one
content-derived value that does carry an order is the commit timestamp, which is what this ticket now
puts in `version`. Evidenced by `the_index_sha256_identifies_content_but_cannot_order_it`. The seen-set
that would let hashes detect a revert changes the on-disk state shape and would collide head-on with
CPE-1940 (PR #1058), so it is deliberately out of scope here.

`model-snapshot.yml` deliberately keeps `date -u +%s`: its content is scraped live on every run, so
publish time genuinely is content time there, and a commit timestamp would freeze the snapshot at its
first published version. That reason is now written next to it and pinned by a test.
